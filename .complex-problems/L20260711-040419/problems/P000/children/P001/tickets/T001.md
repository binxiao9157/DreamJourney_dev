# 构建后端知识治理状态机与权威 Mutation

## Problem Definition

现有 `/kb/mutations` 只校验通用图结构，客户端可以原地改写 evidence 状态或正文，无法证明用户确认、拒绝、纠正保留了历史。需要独立语义层从服务端 snapshot 生成权威 Mutation V2。

## Proposed Solution

新增 `knowledge_governance.py` 纯函数服务和 `POST /kb/governance/actions` owner route。严格解析 schemaVersion、operationId、baseRevision、action、target 和 timestamp；从 snapshot 找到 owner/persona 匹配实体。confirm/reject 更新同一实体状态并附加服务端治理 metadata；correct 把原实体设为 superseded，按实体类型 allowlist 生成稳定 replacement，保留合法关系/来源并追加用户审阅来源。endpoint 使用现有 store mutation 原子提交并返回权威 graph/change metadata。

## Acceptance Criteria

- confirm/reject/correct 对四类实体均有明确合法输入和输出。
- correction 禁止修改 id、owner、persona、privacy/source 与治理字段，只允许实体业务字段。
- correction replacement ID 对同一 operation 稳定，原实体保留 supersededBy，replacement 保留 supersedes。
- facts confirm/correct 同步设置 confidence=confirmed。
- target 缺失、owner/persona 不匹配、非法字段/时间/schema 返回稳定 4xx。
- route ownership、revision conflict、operation ID duplicate 和 change feed 沿用现有合同。

## Verification Plan

新增后端纯函数和 FastAPI 测试，覆盖四类实体、正负状态矩阵、纠正关系净化、重复 operation、revision conflict、跨账号 principal；运行专项 smoke 与后端全量 verify。

## Risks

- replacement 关系可能引用不存在或错误 persona 实体。
- 重试时当前 snapshot 已变化，必须依赖 store 的 operation ID 幂等而非重新解释为新动作。
- governance metadata 不能包含知识正文或敏感 source title。

## Assumptions

- observed 知识仍可按当前策略进入 Echo，用户治理是显式覆盖而不是所有提取的前置审批。
- rejected/superseded 继续由现有 Context filter 排除。
- 本票不实现 Archive 删除编排和 iOS consumer。
