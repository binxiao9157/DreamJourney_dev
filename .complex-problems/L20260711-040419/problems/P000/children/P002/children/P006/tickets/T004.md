# 原子化 Archive 删除与知识来源撤销

## Problem Definition

Archive 删除和知识 revision 当前属于两个独立操作。只调用现有删除会留下仍可生成的知识；先后调用两个 endpoint 又会出现中途失败和并发 mutation 竞态。

## Proposed Solution

为两种 store 增加 `delete_archive_item_with_kb_mutation` 组合原语。调用方提供当前 baseRevision、operationId 和由 governance builder 生成的可选 Mutation V2。Postgres 在一个 connection/transaction 中获取用户 knowledge advisory lock、检查 operation duplicate/current revision、锁定 archive row、校验 sealed、应用 mutation并写 snapshot/change、删除 row，最后统一 commit；任一异常 rollback。MemoryStore 在 archive+knowledge locks 下执行等价操作。

DELETE endpoint 使用 `memoryArchiveItem + itemId` 和服务端 decidedAt 构建 deleteSource；无匹配时传空 mutation但仍校验 revision后删除。query 可选接受 operationId，旧客户端缺失时生成一次性 ID。响应保留旧 `status/id/item` 并增加无正文 `cascade`。

## Acceptance Criteria

- 素材成功删除时，全部直接来源知识已 superseded；Context 不再生成。
- mutation 或 delete 任一步失败时 Postgres 整体 rollback。
- revision race 返回现有 `knowledgeRevisionConflict`，不会先删素材。
- sealed timeLetter 仍返回 409。
- 无知识引用的 archive 可以删除且不产生伪知识 revision。
- 重复 operation 返回幂等结果或稳定可重试状态，不重复 revision。

## Verification Plan

增加 memory、FastAPI、Postgres fake transaction 测试：命中四实体、无命中、sealed、revision conflict、rollback、duplicate、change feed；Context 断言 superseded 不进入 generation。运行全量后端 tests、compileall、diff check。

## Risks

- 复用现有 `apply_kb_mutation` 需抽取 cursor helper，必须保持旧 mutation 幂等和 revision 语义完全一致。
- endpoint 读取 snapshot 到 transaction 之间可能变化，必须由 baseRevision 冲突阻断。
- 旧 archiveImageAnalysis session ref 无法通过 item ID 匹配，需保留明确 legacy gap。

## Assumptions

- 新 Archive 知识来源采用 `memoryArchiveItem + item.id`。
- 删除动作保留知识实体审计历史，仅把状态变为 superseded。
- iOS operation ID 和重试接入在 P003。
