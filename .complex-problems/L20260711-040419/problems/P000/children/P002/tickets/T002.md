# 让 Archive 删除安全级联撤销知识来源

## Problem Definition

Archive 删除当前只删除素材记录，知识 snapshot 中引用该 `memoryArchiveItem` 的实体仍可进入 Echo；同时 Postgres archive 全局 ID 冲突更新会重写 owner。必须先保证来源归属，再把知识撤销和素材删除绑定成同一安全操作。

## Proposed Solution

在治理纯函数中实现 `deleteSource`：按 source kind/id 扫描四类实体，移除目标 ref、把每个命中实体标记 `superseded` 并写入无正文治理 metadata，输出 Mutation V2 和命中摘要。Archive 删除 endpoint 使用 canonical `memoryArchiveItem + itemId` 构建该 mutation，并调用 store 的组合删除方法；Postgres 在同一 transaction/knowledge advisory lock 下校验 base revision、应用 mutation、写 change feed、删除 archive row，内存 store 使用同一锁语义。无命中时仍在知识 revision 检查下删除。修复 archive ID 跨 owner conflict，映射稳定 409。

## Acceptance Criteria

- deleteSource 精确匹配四类实体的 `(kind,id)`，不按 title 或模糊字符串删除。
- 所有命中实体移除目标 ref、保留其他 refs 和历史正文、状态变为 superseded。
- Archive 删除成功后 snapshot/Context 中旧知识不可生成，change feed 可解释；任一步失败不出现“素材已删但知识仍活跃”。
- sealed timeLetter 继续不可删除。
- 相同 archive ID 不可被另一 owner 覆盖；同 owner 更新继续兼容。
- Postgres rollback、revision race、无知识引用、重复请求和内存实现有测试。

## Verification Plan

新增 source cascade endpoint/store 测试，扩展 Postgres store 测试覆盖组合事务 rollback、owner conflict 与并发 revision；Context 测试验证级联后 filtered reason/生成文本不含旧实体；运行后端专项和全量测试。

## Risks

- 重构 Postgres mutation transaction 容易破坏现有幂等与 change feed。
- 旧 image-analysis source ID 不是 archive item ID，只能明确为 legacy migration gap，不能假装已级联。
- 无知识命中时也必须锁定 revision，避免删除同时新写入来源实体。

## Assumptions

- 新数据统一使用 `memoryArchiveItem` 与真实 archive item ID。
- 源删除采用审计保留的 supersede，而非知识 tombstone。
- iOS 删除调用与 legacy source migration 由独立子票处理。
