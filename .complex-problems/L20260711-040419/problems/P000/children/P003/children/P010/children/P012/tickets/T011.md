# 串行提交治理 Outbox 并处理 Revision/Generation

## Problem Definition

Outbox 只保证动作不丢；若不接入现有 coordinator，治理和 graph sync 可能并发，409 无法重试，旧 user/persona callback 也可能覆盖当前状态。

## Proposed Solution

扩展 `KnowledgeSyncCoordinator`：增加 outbox store、completion map 和 `performGovernance`/`resumePendingGovernance`。提交前验证 backend auth/current user/expected identity，先 enqueue 再调度。`startNextGovernanceIfPossible` 与普通 sync 共用 `isSyncing` 和 serial queue，选择当前 persona 匹配 item，基于 base revision 调 client。成功且 identity 仍匹配时应用权威 snapshot并移除 item；persona 已切换时移除服务端已完成 item但不直接 apply，转入 change-feed sync。409 保留 item、refresh后同 operation重试；其他失败保留 item并完成失败回调。

## Acceptance Criteria

- outbox 写入发生在 client 调用前。
- 普通 sync/governance 不并发且可 coalesce。
- 成功更新 base/graph并删除 item；失败保留。
- 409 刷新后重试同 operation。
- user generation 变化完全忽略旧 callback；persona 变化不直接 apply。
- completion 主线程、日志不含 action正文；提供 pending count 供 QA。

## Verification Plan

新增 coordinator static guard 覆盖关键调用顺序、identity checks、retry和 stale path；扩展 outbox/model smoke。运行完整 Simulator build，P004 再做 release regression。

## Risks

- `applySyncedGraph` 会触发新 sync，需要正确设置/清除 isSyncing 和 needsResync。
- server success 后本地 apply 失败必须保留 outbox，以同 operation duplicate response 恢复。
- 当前 persona 不匹配的 item 可能长期 pending，QA count必须可见。

## Assumptions

- 单例 coordinator 的 serial queue 是知识网络 owner。
- 当前 graph 按 user 存储多 persona，但产品要求旧 persona callback 不直接驱动本地完成态。
