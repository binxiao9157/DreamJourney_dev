# 实现持久化 Governance Outbox 与串行重试

## Problem Definition

治理 action/client 已存在，但直接调用会在离线、App 重启、revision conflict 或 user/persona 切换时丢失动作或错误应用旧响应。现有单槽 graph pending mutation 不适合多条显式治理动作。

## Proposed Solution

在 `KnowledgeThreeWayMerge.swift` 增加 Codable outbox item/store，按 user hash 独立 JSON 文件、原子写入、operation ID 去重。在 `KnowledgeSyncCoordinator` 提供 `performGovernance(action:expectedIdentity:completion:)`：动作先持久化，随后与普通 sync 共用 serial queue/isSyncing。只处理当前 user 且 expected identity 匹配的 item；基于 remote base revision 调用 client。成功且 identity 未变时应用 authoritative graph、保存 base、删除 outbox；identity 已变时不直接 apply，删除已成功 item并触发 change-feed refresh。409 保留同 operation ID，刷新后重试；其他失败保留 outbox。

## Acceptance Criteria

- outbox 多项、有序、按 user 隔离、重复 operation upsert、损坏文件安全移除。
- governance 与普通 sync 同时最多一个网络 owner。
- 成功删除 item并更新 base；网络失败保留；409 refresh 后重试同 operation。
- user generation 变化丢弃旧 callback；persona 变化不直接应用响应，改走 change feed。
- completion 回主线程且不包含知识正文日志。
- 无公开 UI 变化。

## Verification Plan

新增 Swift outbox model smoke（临时目录 round-trip/隔离/删除/损坏恢复）和 coordinator static guard（持久化先于网络、identity checks、409 retry、authoritative apply）。运行 governance/three-way model smoke、Simulator build，最终 release regression 在 P004。

## Risks

- KBLite apply 会触发普通 sync，必须 coalesce 防循环。
- persona 不匹配 item 若永远不回到该角色会留在 outbox；需提供 QA 可见 pending count，后续产品可决定取消策略。
- 服务端成功但客户端断线会重试；operation ID 幂等必须保持不变。

## Assumptions

- KBPersonaIdentity 可安全扩展 Codable/持久化或由 outbox 存三个字符串。
- 每用户治理动作量很小，JSON 数组足够，无需数据库。
- 本轮不实现用户可见待处理队列。
