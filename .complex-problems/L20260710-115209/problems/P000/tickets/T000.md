# 实现可持久化的音色槽独占分配与合成授权

## Problem Definition

当前试用/控制台音色池使用逻辑 profile ID 哈希取模选择 `S_` 音色。不同用户或角色可能碰撞到同一 provider speaker，后一次训练会覆盖前一人的声音。`/voice/synthesis` 也没有先验证 profile 的所有权、启用状态与质量验收状态，存在错误音色和越权合成风险。

## Proposed Solution

在内存和 Postgres store 中增加 provider speaker slot 记录与原子分配接口。App 继续使用逻辑 `voiceProfileId`，后端将其绑定到独占的 `providerSpeakerId`，并在训练、查询和合成时内部解析。训练状态同步到 slot；禁用保留占用；删除将 slot 标记为 retired，避免跨用户复用残留音色。旧的 `voiceProfileId=S_...` profile 走兼容解析。合成入口必须加载持久化 profile，验证用户归属、ready/enabled/quality accepted，再调用 provider。

## Acceptance Criteria

- 同一 configured provider speaker 同时最多绑定一个有效逻辑 profile。
- 三个 provider speaker 已占用时，第四个新 profile 返回明确的 HTTP 409 capacity error。
- 重复提交同一逻辑 profile 复用原分配，不重新占用其他槽。
- 训练、refresh 与 synthesis 使用 `providerSpeakerId`，API 返回和 iOS 绑定继续使用逻辑 `voiceProfileId`。
- 合成拒绝不存在、跨用户、pending、failed、disabled、deleted 或未质量验收的 profile。
- 删除后的 provider slot 进入 retired，不自动分配给其他用户。
- 旧 `S_` profile 在满足可用条件时仍可合成。
- 后端完整测试、静态 QA、iOS Debug 构建与 `git diff --check` 通过。

## Verification Plan

先补 store 和 API 失败测试，再实现 schema/store/service。运行后端单测和 FastAPI smoke，增加静态合同检查覆盖逻辑/供应商 ID 分离和禁止哈希分配。更新 iOS 逻辑 ID前缀并运行相关 Swift 检查与模拟器 Debug 构建，最后执行两个仓库的 `git diff --check`。

## Risks

- 现有数据库中的 `S_` profile 没有 slot 记录，需要兼容而不能强制迁移失败。
- provider 训练失败后是否可重试必须继续绑定原槽，不能把可能含有声音数据的槽发给其他用户。
- Postgres 分配必须使用单条带锁语句或等价原子操作，避免并发抢占同一槽。

## Assumptions

- 当前三个 `S_` 槽用于 QA/试用，生产扩容需要另行购买或切换后付费资源。
- iOS 不需要知道真实 provider speaker ID。
- 本任务不改变腾讯数字人会话、公开 UI 和真机流程。
