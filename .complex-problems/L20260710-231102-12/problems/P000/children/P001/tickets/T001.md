# 在现有 KB snapshot 上增加兼容的增量同步层

## Problem Definition

当前 `/kb/sync` 直接覆盖用户整份 graph，store 只返回 snapshot，没有 revision 和 operationId。客户端重试无法证明幂等，多设备也无法按版本拉取变化；但 ContextPacketBuilder、现有 smoke 和旧客户端都依赖 snapshot 结构，不能破坏现有接口。

## Proposed Solution

在 store 层引入 `KnowledgeSnapshotRecord` 语义：graph、revision、updatedAt、appliedOperationIds 和按 revision 记录的 change log。现有 `/kb/sync` 写入时生成一次 replace change；新增 owner-bound `/kb/mutations` 接收 operationId、baseRevision 和 graph replacement/merge mutation；新增 `/kb/changes/{userId}?sinceRevision=` 返回顺序变化及当前 revision。InMemory 与 Postgres 实现同一行为，Postgres 使用事务和唯一 operationId 保证并发幂等。`get_kb_snapshot` 保持只返回 graph，避免破坏 ContextPacketBuilder。

## Acceptance Criteria

- 首次 sync 返回 revision，旧响应字段不删除。
- 重复 operationId 返回相同 revision 且不新增 change。
- sinceRevision 只返回更新版本，包含可恢复当前 graph 的兼容 payload。
- baseRevision 冲突返回明确 409 和 currentRevision。
- owner principal 访问其他用户 mutations/changes/snapshot 返回 403。
- InMemory/Postgres 单测和 FastAPI smoke 覆盖上述合同。

## Verification Plan

运行知识 store 单测、核心 API 单测、authorization policy 单测、FastAPI smoke 和新建 backend KB delta smoke；最后运行后端全量 unittest 与 `git diff --check`。

## Risks

- 现有 store 方法由 ContextPacketBuilder 直接消费，返回类型不能直接改成 record。
- Postgres migration 需要兼容已存在的 `kb_snapshots` 行。
- change log 不能保存未经过 privacy filter 的 graph。

## Assumptions

- P0 mutation 可以先支持受控的 graph replacement，不在本任务实现通用 JSON Patch。
- change feed 主要供 iOS 同步，不作为家庭共享审计日志。
- change retention P0 可保留有限最近记录，完整压缩策略后续处理。
