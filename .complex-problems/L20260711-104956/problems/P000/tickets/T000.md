# 建立稳定水位分页与终页提交

## Problem Definition

当前后端一次返回用户全部知识变更，数据增长后响应无界；iOS 假设一次请求到达最新 revision，任何直接分页都会在中间页失败或提前提交、清 pending 和发送 mutation。分页窗口还会放大本地提取与远端 apply 的覆盖竞态。

## Proposed Solution

后端提供显式 limit + 固定 targetRevision 的 revision 水位分页，保留无 limit 的旧合同。iOS 增加无副作用 page reducer，只保留最终权威 snapshot；Coordinator 在终页后一次提交，并用 KBLite graph mutation version/CAS 在本地变化时重算 merge。正常同步和 409 refresh 共用状态机。

## Acceptance Criteria

- 后端分页不追逐 target 后的新 revision，严格升序且有界，旧请求行为不变。
- iOS 中间页不写 base/KBLite、不清 pending、不发送 mutation/governance。
- malformed、循环、无进展、target 改变和旧 generation 页被拒绝。
- 分页期间本地知识写入通过 CAS 重算保留。
- 非真机全量测试、release regression 和两类构建通过。

## Verification Plan

分别验证后端 Memory/Postgres/API 三页与固定 target；运行 iOS reducer/CAS model smoke、Coordinator source gate、跨仓分页 gate、release regression、Simulator 与 generic iPhoneOS build。

## Risks

- 中间页副作用会造成 base/pending 不一致。
- 后端 target 未固定会导致连续写入时永远追页。
- CAS 若未覆盖全部本地写路径仍可能丢知识。
- 旧后端分页字段缺失必须只按单页终态兼容。

## Assumptions

- 每个知识 revision 都有对应 change，且 change 当前携带完整 graph。
- 本轮不做 compaction、部署或真机。
