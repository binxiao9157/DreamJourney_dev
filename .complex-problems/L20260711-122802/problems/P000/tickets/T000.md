# 统一知识 mutation 隐私格式并清洗持久化历史

## Problem Definition

V2 snapshot graph 已使用服务端 canonical source title，但 normalized mutation 仍保留客户端原始 title，并被写入 API 响应、change feed 与 operation receipt。该分叉会持久化不可信或敏感标题，且重复操作的 payload hash 受到非语义 title 影响。线上历史 JSONB 也需要可审计、可回滚、幂等的规范化处理。

## Proposed Solution

将 mutation canonicalization 提升为 knowledge_store 的单一入口，在 fingerprint、merge、持久化和回包前完成。分别在 InMemory/Postgres 证明首次写入与 replay 一致；新增 Postgres maintenance service/CLI 以 dry-run 和事务 apply 清洗 snapshots、changes、receipts，并只对可证明输入的 `kb.mutation` V2 receipt 重算 hash。最后增加跨仓 gate、release 防回退、文档、提交部署与线上 dry-run/apply/dry-run 证据。

## Acceptance Criteria

- 首次响应、change feed、receipt、duplicate replay 都不含客户端 raw source title。
- raw/canonical title 重试保持幂等；source kind/id/正文变化仍冲突。
- maintenance dry-run 不写入，apply 保留业务身份/revision 并幂等归零，异常完整回滚。
- 报告只返回聚合计数，不泄露正文、source ID、用户 ID 或 token。
- 后端全量、跨仓 gate、iOS generic builds、release regression 和线上 Postgres 清洗验收通过。

## Verification Plan

拆分为新写入 canonicalization、存量 maintenance、跨仓交付部署三个子问题；各自使用 sentinel tests，最后执行线上 dry-run/apply/dry-run 并保存脱敏摘要。

## Risks

- receipt payload hash 不能对无法还原原始 semantic payload 的 operation kind 猜测重算。
- maintenance 必须与知识 mutation 使用互斥锁并在单事务中执行。
- 生产 apply 只允许 canonical metadata 修复，不改变 source identity 或用户正文。

## Assumptions

- `source_ref_title(kind)` 是当前服务端 title 权威表。
- 后端 main 仍是部署分支，iOS 当前 feature 分支用于 QA 和文档接线。
- 不做真机或公开 UI 变更。
