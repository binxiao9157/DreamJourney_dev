# 以单事务维护服务规范历史知识隐私 metadata

## Problem Definition

线上 `kb_snapshots.graph`、`kb_changes.graph/mutation` 和 `kb_operation_receipts.result` 可能包含新合同生效前保存的 raw source title。清洗必须可预览、可回滚、幂等，不能破坏 operation replay。

## Proposed Solution

新增纯函数 canonicalize persisted graph/mutation/result，并在 PostgresStore 中实现 `maintain_knowledge_privacy_metadata(apply=False)`：先获取全局 maintenance lock，枚举用户并按排序获取 `knowledge:{userId}` 锁，在单事务内扫描三张表。dry-run 只统计；apply 仅更新变化的 JSONB。对于 operation_kind=`kb.mutation` 且 schema_version=2 的 receipt，用 canonical mutation 重算 payload hash；其他 operation hash 保持。新增默认 dry-run CLI，输出固定 schema 的脱敏聚合报告。

## Acceptance Criteria

- snapshot/change/receipt 三类记录均被扫描和规范化。
- 不改 user/entity/source ID、正文、revision、operation ID、createdAt。
- dry-run 无 update；apply 后第二次 apply 更新为 0。
- `kb.mutation` V2 重放 hash 与新 canonical fingerprint 一致，其他 operation hash 不变。
- 任意 update 失败时整个事务 rollback。
- CLI 默认 dry-run，报告仅含模式、扫描/更新计数和错误数。

## Verification Plan

使用纯函数 tests 与扩展 FakeConnection 覆盖 dry-run/apply/idempotence/hash/rollback；CLI contract test 防止默认 apply 或输出记录内容；运行定向和全量后端验证。

## Risks

- 全局锁不能替代 per-user knowledge lock；两者都需要。
- 非 V2 或无法证明 semantic payload 的 receipt 不重算 hash。
- 遇到无法规范化的 V2 mutation 时 apply 必须失败回滚，不能静默部分清洗。

## Assumptions

- 当前数据量允许一次受控维护窗口内的单事务扫描。
- 生产执行顺序固定为 dry-run、备份确认、apply、post-apply dry-run。
