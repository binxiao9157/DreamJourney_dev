# 固化隐私 gate 并完成双仓发布与线上清洗验收

## Problem Definition

新写入 canonical mutation 与历史维护工具已经通过后端单元测试，但尚未进入 iOS/release QA 防回退，也尚未在真实生产 Postgres 上验证锁、JSONB 更新、receipt hash 和存量归零。必须用可重复脚本连接代码合同、构建、发布和线上清洗证据，避免只凭单元测试宣布完成。

## Proposed Solution

1. 新增后端 maintenance contract smoke，使用隔离的 Postgres fixture 或线上受控路径验证 default dry-run、apply、二次 dry-run、V2 receipt replay 与脱敏聚合输出。
2. 新增 iOS 侧静态 gate/QA runner，检查 mutation/receipt/change canonical 合同和维护脚本仍被 release QA package 引用，不改变公开 UI。
3. 将可选知识隐私 gate 接入现有 release regression，运行后端全量、iOS 相关静态检查、模拟器或可用替代 smoke、generic iPhoneOS build 与 diff check。
4. 后端与 iOS 分仓提交并推送；部署后端，确认 production/Postgres health 与版本。
5. 生产执行备份确认、dry-run、`--apply`、post-apply dry-run；保存只含聚合计数的报告，要求最终 changed 全为 0，且线上新 V2 mutation 的 response/change/receipt/replay 不含 sentinel raw title。

## Acceptance Criteria

- release QA 对 canonical mutation 与 maintenance 默认 dry-run 形成可重复防回退检查。
- 后端全量测试、知识 smokes、release regression、git diff --check 通过。
- iOS Simulator/非真机 smoke 与 generic iPhoneOS build 通过；不得用真机结果替代。
- 两仓分别形成清晰提交并推送当前分支。
- 后端服务器拉取新提交并重建运行，health 明确为 production/Postgres。
- 生产维护按 dry-run/apply/dry-run 顺序执行；报告不含 user/source/entity ID、正文或 token，最终所有 changed 计数为 0。
- 线上新 mutation 的首次响应、change feed、receipt replay 使用同一 canonical title；raw sentinel 不出现。
- 不修改 Stitch UI，不扩展 Widget/Family/semantic cache/compaction/source identity 范围。

## Verification Plan

- 后端：`scripts/verify_backend.sh`、maintenance 定向测试、部署 smoke、线上 V2 mutation sentinel smoke。
- iOS：知识静态检查、release QA package、Simulator smoke（若环境可用）、generic iPhoneOS build。
- 数据：生产维护三阶段聚合 JSON 对比；apply 前确认数据库备份可用，apply 后再次 dry-run 证明归零。
- Git：双仓 `git diff --check`、提交历史、远端分支与服务器版本核对。

## Risks

- 生产表锁会短暂阻塞知识写入；维护需在低流量窗口执行并设置可控超时。
- 历史无效结构会让 apply 整体拒绝；必须先看 dry-run invalidRecordCount，不能绕过后局部清洗。
- 线上测试不得输出真实 token、用户或知识内容；sentinel 数据必须使用新建 QA 账号和合成内容。

## Assumptions

- 服务器 SSH、私密部署 token 和数据库容器访问方式仍可用。
- 生产数据库在 apply 前有可恢复备份。
- 本任务不要求真机，Simulator 不可用时必须保留 generic iPhoneOS build 与静态/合同 gate 的明确证据，不能虚构截图。
