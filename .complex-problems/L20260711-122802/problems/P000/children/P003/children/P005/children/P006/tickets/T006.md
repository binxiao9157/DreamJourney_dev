# 安全部署并证明生产清洗可执行

## Problem Definition

生产尚未运行 Task 20，不能直接 apply。需要先部署目标提交、确认服务和 Postgres，再创建可恢复备份并执行只读 dry-run，任何异常都必须在写入前阻断。

## Proposed Solution

- 通过 `miao-server` 探测仓库、compose 服务、数据库容器和磁盘，不修改 `.env`。
- `sudo -u miao -H git pull --ff-only origin main` 拉取并用 compose 重建 API，核对 HEAD/health。
- 从 compose 配置解析数据库服务名，在服务器私密目录创建时间戳 `pg_dump` custom-format 备份；权限 600，检查非空和 SHA-256。
- 在 API 容器中运行 maintenance 默认命令，保存 stdout 至服务器私密 600 JSON；用独立 Python 只校验 schema/mode/status/invalid/count keys。
- 若 invalidRecordCount 非零、备份失败或 health/版本不符，停止并记录，不运行 apply。

## Acceptance Criteria

- API 运行提交 `e1f06a8`，health production/Postgres。
- 备份存在、非空、600、有 SHA-256，且路径不在 Git 仓库公开目录。
- pre-dry-run 成功且 invalidRecordCount=0，报告不含用户 ID、知识正文或 token。
- 本步骤没有执行 `--apply`。

## Verification Plan

- SSH 输出只保留 SHA、health 摘要、容器状态、备份元数据和 dry-run 聚合计数。
- 用 grep/JSON schema 断言报告键集合，不打印原始生产行。
- 部署后从公网 `/health` 再验证一次。

## Risks

- compose service 名称或数据库凭据可能不同，先 inspect 配置，不猜测。
- `pg_dump` 可能占用磁盘；先检查可用空间，失败立即停止。

## Assumptions

- SSH alias、sudo Docker、服务器仓库路径仍有效。
- 服务器容器镜像包含应用脚本与 Python 依赖。
