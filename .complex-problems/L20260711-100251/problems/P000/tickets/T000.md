# 建立权威知识操作凭据并恢复客户端冲突

## Problem Definition

当前后端只按用户和 operation ID 去重，不验证同一 operation ID 是否仍对应相同语义 payload；不同知识写入、治理动作或 Archive 删除可能被静默当成首次请求的重复操作。iOS 对新冲突也没有终止或恢复策略，poisoned item 会永久阻塞治理队列。

## Proposed Solution

在后端建立独立 operation receipt，使用 canonical JSON 和 SHA-256 记录 operation kind 与规范化 payload 的语义指纹，并把 receipt 与 KB snapshot、change feed、Archive 删除置于同一事务。相同指纹安全重放，不同指纹返回结构化 409；旧 change 继续兼容但标记为未验证。iOS 将错误解析为强类型 disposition，普通 mutation 清理 poisoned pending 后刷新并用新 ID 重建，治理动作首次旋转、再次冲突隔离，且隔离项不阻塞后续队列。

## Acceptance Criteria

- 新 operation ID 无法静默复用到不同 payload、schema、operation kind 或 Archive item。
- 相同语义 payload 在 base revision 改变后仍可幂等重放。
- 无 KB 级联的 Archive 删除也可原样重放，且不会污染 change feed。
- legacy change 保持兼容，并明确返回 operationPayloadVerified=false。
- Governance 原样 action 可重放，不同 action 返回 409；iOS 冲突恢复不形成无限循环。
- 公开产品 UI、Echo 上下文和用户正文不受影响，hash 不出现在 API 响应或日志正文中。

## Verification Plan

运行后端 memory/Postgres 单元测试、知识治理组合 gate 和全量测试；运行 iOS model smoke、client/coordinator static checks、知识治理 gate、release regression、Simulator workspace build 与 generic iPhoneOS build；最后执行两个仓库的 git diff --check 并分别提交。

## Risks

- Receipt 与业务写入若不在同一事务会造成错误回放或重复执行。
- Governance mutation 依赖当前 snapshot，必须在构建 mutation 前检查稳定 action receipt。
- Legacy 行无法还原原始 payload，不能伪造可信 hash。
- iOS outbox Codable 变化必须兼容旧持久化文件。

## Assumptions

- operation ID 在单个用户范围内唯一。
- baseRevision 是并发前提，不属于稳定业务 payload 指纹。
- 当前任务不执行线上数据库迁移、部署或真机验证。
