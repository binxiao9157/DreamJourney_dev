# 实现 iOS 知识操作冲突恢复

## Problem Definition

客户端无法精确区分 revision 与 payload conflict；普通 mutation 会永久复用 poisoned operation ID，治理 outbox 会让冲突项持续阻塞队列，并允许相同 ID 被不同 action 覆盖。

## Proposed Solution

为 backend error 增加稳定 code 解析和 conflict disposition；普通 mutation 遇到 payload conflict 时删除旧 pending、保留本地图谱并刷新后重建。Governance outbox 增加 recovery count 和 quarantine reason，首次冲突原子旋转 ID，第二次隔离并继续后续队列；修正重复 enqueue 与 operation ID 规范化。

## Acceptance Criteria

- Coordinator 精确识别 payload conflict，且不触发 V2->V1 fallback。
- 普通 pending 冲突后不再复用旧 ID，本地知识修改不丢失。
- Governance 第一次冲突旋转，第二次 quarantine；隔离项不自动重放、不阻塞后续项。
- 相同 ID/相同 action enqueue 幂等，不同 action 本地拒绝；旧 outbox JSON 可读取。
- QA model smoke 和源码门禁覆盖状态机。

## Verification Plan

运行 outbox model smoke、three-way merge smoke、client/coordinator checks、knowledge pipeline 和 governance gate，再运行编译与 release regression。

## Risks

- completion 必须随 operation ID 旋转迁移，避免调用方永远收不到结果。
- quarantine 写盘失败时不能错误声称已终止。
- 刷新权威 base 时 applyAuthoritativeRemote 会清 pending，需确保本地图谱合并保留 intent。

## Assumptions

- Backend 409 detail 包含稳定 error code 和 operation ID。
- 本轮只提供 QA 证据，不增加公开 UI。
