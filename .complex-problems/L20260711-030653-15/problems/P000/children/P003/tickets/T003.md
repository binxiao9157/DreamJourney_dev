# iOS 消费 Mutation Proposal 并绑定 Persona Identity

## Problem Definition

iOS 仍只解码 provider extraction、随机生成 ID，并在异步完成时只校验用户 generation；提取 summary 和本地 fallback 也未按实体 persona 过滤。

## Proposed Solution

先增加兼容 proposal/envelope/persona metadata 模型与 backend client 解码，再改 KBLite 合并为 proposal-first、legacy fallback，并在会话结束捕获 canonical identity。所有 summary、local extraction 与 generation fallback 按 identity 过滤，异步结果 identity 变化时丢弃。

## Acceptance Criteria

- proposal 可解码且响应 identity 必须与请求一致。
- proposal ID、关系、source/evidence/persona metadata 被持久化，local natural match 不重复。
- 旧 server extraction 与旧本地文件继续可读。
- 提取期间用户/角色切换会丢弃旧结果。
- personal 兼容 legacy；family 只匹配显式 metadata，summary/fallback 不跨 persona。

## Verification Plan

新增纯 Swift model/policy smoke、静态 source guard、release regression 与 generic builds；不做真机。

## Risks

- 本地未同步 legacy ID 与服务端稳定 ID 可能不一致，需要 proposal-to-local ID remap。
- KBLiteModels 是广泛使用的 Codable schema，新增字段必须 optional 保持旧文件兼容。

## Assumptions

- 后端 proposal 不包含新实体时间戳时，iOS 可安全使用本地当前时间。
- KnowledgeSyncCoordinator 继续负责最终 Mutation V2 提交和 revision 冲突。
