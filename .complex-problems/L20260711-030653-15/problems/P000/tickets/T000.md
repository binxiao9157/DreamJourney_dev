# 落地可审计知识 Proposal 与 Persona 归属

## Problem Definition

当前 `/kb/extract` 只返回 provider 形态 extraction，iOS 使用随机 UUID 和本地名称匹配合并，导致重试/多端实体身份不稳定、关系无法可靠解析，且实体缺少 owner/persona/evidence 元数据。家庭 persona 因此不能安全消费目标角色知识。

## Proposed Solution

在后端新增纯函数 proposal builder，基于服务端权威 snapshot 完成自然键规范化、旧 ID 复用、稳定 ID 生成、关系解析和来源/隐私/persona 继承；`/kb/extract` additive 返回非持久化 `mutationProposal`。iOS 增加兼容模型并优先合并 proposal，捕获请求发起时的 canonical identity，旧服务端继续走 extraction 降级。Context 对 personal 旧数据兼容，对 family 只读取显式匹配 `personaScope/digitalHumanId` 的事实。

## Acceptance Criteria

- 相同 owner/persona/自然键生成稳定 ID，snapshot 已有实体复用原 ID。
- proposal 可直接用于 Mutation V2，包含 revision、来源、隐私、persona 和 evidence metadata，且不自动写库。
- 人物、地点、事件与事实关联只指向有效 snapshot/proposal ID。
- iOS 在 user/persona 切换后丢弃旧回调，并兼容旧 extraction。
- family Context 只消费目标 digitalHumanId 的 family facts，个人旧数据不会越界。
- Task 12-14 回归、后端测试、release regression 和 generic builds 通过。

## Verification Plan

1. 后端单测覆盖稳定 ID、legacy ID 复用、关系解析、metadata、空/非法 persona 与 endpoint 合同。
2. Context 测试覆盖 personal legacy、family match、family mismatch 和跨 owner 过滤。
3. iOS Swift smoke 覆盖 proposal decoding、identity policy、legacy fallback 和 persona metadata。
4. 运行后端全量 verify、跨仓库 knowledge gate、release regression、generic Simulator/iPhoneOS build 与 `git diff --check`。

## Risks

- 名称自然键可能合并同名不同人；本轮只做确定性保守匹配，后续用户治理处理歧义。
- 旧数据没有 persona metadata；仅 personal/self 兼容，避免推断 family 权限。
- proposal 基于 baseRevision，提交前可能发生冲突；继续由现有 Mutation V2 409/三方合并处理。

## Assumptions

- 后端 snapshot/revision 是 proposal 去重的权威来源。
- iOS 当前用户拥有本地 KBLite 文件；知识实体不能自行授予家庭访问权限。
- 本轮不改变公开 UI，不做真机或真实 provider 质量验收。
