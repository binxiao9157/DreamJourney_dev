# 用显式 owner/source/status 决定家庭关系权限

## Problem Definition

FamilyMember 目前没有 authority source，普通 initializer 与 legacy decode 缺字段时默认 active/accepted，使 KBPerson、mock 和历史本地对象与后端已接受手机号邀请无法区分。

## Proposed Solution

新增 `FamilyRelationshipAuthoritySource`、`FamilyRelationshipAuthorizationContext` 和纯 `FamilyRelationshipAuthorizationPolicy`。FamilyMember 持久化 `relationshipOwnerUserId` 与 `relationshipAuthoritySource`，`isAcceptedFamilyMember` 通过当前登录 owner 和生产策略计算；后端 parser 显式标记 backend invitation，legacy/default 标记 unverified 并使用 pending 状态。QA fixture 必须显式 source 且只在 allowQA context 下通过。

## Acceptance Criteria

- 缺 owner/source、legacy/default、本地普通对象均不 accepted。
- 当前 owner + backendInvitation + active + accepted 才通过生产策略。
- owner mismatch、pending、failed、revoked、knowledgeCandidate 均拒绝。
- qaFixture 在生产拒绝，显式 QA context 可通过。
- fromBackendJSON 读取 ownerUserId/userId 并标记 backendInvitation。
- 纯 Swift model smoke 运行通过。

## Verification Plan

新增独立 model smoke，编译 MemoryModel 与 policy，覆盖所有状态组合、legacy JSON decode 和后端 JSON parse；运行静态 grep 确认不再存在 active/accepted 默认值。

## Risks

- 依赖旧 initializer 默认 accepted 的 UIQA fixture 会失败，后续 repository 子问题必须显式标记 QA source。
- isAcceptedFamilyMember 读取当前 UserManager 会降低模型纯度，因此属性应委托 context-aware 方法，默认生产 context 只用于 app 消费。

## Assumptions

- 后端 payload 总能提供 `ownerUserId` 或 `userId`；两者都缺失时必须拒绝。
- existing pending/failed backend parser 语义保持不变。
