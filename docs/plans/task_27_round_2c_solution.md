# Round 2C 产品决策登记册与底稿生命周期方案

## Problem Definition

Round 1 的 21 项冲突混合了可由安全原则固定的默认值、需要产品确认的范围、依赖合规/商业/供应商的外部决定以及纯工程证据问题。现有四份底稿又缺少生命周期标识，容易被后续开发误认为同等权威。

## Proposed Solution

1. 建立结构化产品决策登记册，包含状态、决策类型、冲突来源、推荐、替代选项、影响、默认安全策略、责任角色、决策门和证据链接。
2. 覆盖 C-01 至 C-21，并把独立复审发现的成人范围、第三方权利、AI 身份披露、危机延迟、单位成本、管理员访问和供应商退出等新增决定纳入。
3. 仅把用户当前明确允许修订底稿的口径标为 `CONFIRMED`；其余重要产品选择标记 `RECOMMENDED_PENDING`、`EXTERNAL_REQUIRED`、`DEFERRED` 或 `REJECTED`。
4. 对未决项设置服务端 fail-closed 默认值、进入开发前门槛和责任角色，确保工程不会用 UI 或实现细节替产品决定。
5. 在四份底稿顶部加入 lifecycle banner：历史/评审/静态分析状态、可用于什么、不可用于什么、V4 权威链接和修改说明；不删除历史正文。
6. 建立静态检查，验证 21 个冲突均覆盖、状态合法、关键决定存在且源文档 banner 完整。

## Acceptance Criteria

- 决策登记册覆盖 C-01 至 C-21，无缺号，且每项字段齐全。
- 新增成人/第三方、AI 身份与危机、安全管理员、地域/处理商、单位成本等决策。
- 重大未决项均有 fail-closed 默认和明确进入门，不把推荐写为已确认。
- PRD、Blueprint、iOS 分析和 Hermes/AOS 分析均标明不是最终执行依据并链接 V4。
- 原始正文保留，修订通过 banner/变更记录可追溯。
- 静态检查和 `git diff --check` 通过。

## Verification Plan

1. 自动提取 evidence matrix 的 C-01..C-21，与登记册集合比较。
2. 校验登记状态枚举、责任角色、决策门和 fail-closed 字段非空。
3. 检查四份底稿的 lifecycle banner 和 V4 链接。
4. 检查 `CONFIRMED` 只用于有 E2 证据的决定。
5. 运行 Product V4 文档检查和 `git diff --check`。

## Risks

- 登记册过度细碎，失去对开发顺序的约束力。
- 把安全推荐误当成商业决策已获批准。
- 直接重写源文档导致历史要求不可追溯。
- 用 `DEFERRED` 掩盖实际阻断项。

## Assumptions

- V4 是最终产品成果物，源 PRD/Blueprint/分析文档可以修订和标记为历史底稿。
- 身份、地域、处理商、声音/肖像、删除 SLA 和成本上限仍需要有权人确认。
- 安全默认可以先进入工程计划，但公开启用仍受决策门约束。
